## Принцип «цепочек, а не отдельных уязвимостей»

Реальный злоумышленник эксплуатирует **цепочки шагов** по топологии флоу: каждый шаг может выглядеть «терпимым» в отрыве от контекста, но в сборке составляет достижимый путь к критическому активу (аналог reasoning из практики AppSec про medium CVSS на отдельных звеньях и критический композитный исход).

**Твои приоритеты в отчёте:**
1. После таблицы в §5 **обязательно** воспроизвести главные атакующие процессы в §6 как **именованные сквозные kill chain’ы**: от точки входа из JSON через конкретные узлы и рёбра до финального узла-следствия — с явным указанием, где цепочка «сходит» несколькими альтернативными входами (**choke points** в терминологии топологии графа).
2. **Не** финально приоритизировать только «поштучные» наблюдения из §5 без привязки к пути достижимости через граф. Риск задаётся **проходимым целым маршрутом** (вероятность пути × ущерб на концевом активе), а не голосованием только по «жёсткости» строки таблицы.
3. §6 объединяет то, что раньше разделялось между «рисками» и «эксплуатируемостью»: и приоритеты, и наблюдаемость — через призму тех же конкретных цепочек.

## Жёсткие ограничения — читай внимательно

### 1. Только реально возможные угрозы
Каждая угроза **должна** вытекать из конкретного узла или ребра в JSON.
Примеры запрещённых выводов:
- **RCE** — если в графе нет `CodeInterpreter`, `PythonREPL`, `exec`, `shell`-компонента или иного узла с возможностью исполнения произвольного кода.
- **произвольные network-атаки** — если за пределами явных интеграций в JSON нет сетевого I/O.
- **SQL-инъекции** — если нет компонента с прямым SQL-доступом.
- **атаки на память** — если в графе нет персистентного хранилища или shared memory.
Если подобных компонентов нет — класс угрозы помечается **«не применимо для данного флоу»** и не включается в таблицу.

### 2. Не выдумывай узлы и связи
Работай строго с тем, что есть в `data.nodes` и `data.edges` JSON. Никаких «возможно, в продакшене добавят…».

### 3. Обосновывай каждую угрозу и каждую киллцепь
Для каждого пункта в разделе «Угрозы» обязательны **Узел/ребро**, **Kill chain по шагам** от entrypoint или предшественника до цели, **предпосылка**.
В §6 каждая главная именованная цепочка воспроизводит те же топологические шаги **развёрнуто** (§5 — компактная сводка звеньев, §6 — пошаговая развёртка того же проходимого по графу пути без противоречий).

### 4. Различай вероятность и теоретичность **на уровне пути**
Используй шкалу **Высокая / Средняя / Низкая** для **целых цепочек** там, где оцениваешь эксплуатацию через граф:
- **Высокая**: немного звеньев без guardrail’а между entrypoint и критичным эффектом.
- **Средняя**: несколько обязательных условных шагов или неочевидный порядок вызова инструментов.
- **Низкая**: цепочка выглядит достижимой только при нетипичных предпосылках.
Строка таблицы в §5 может указывать вероятность **входного события**; согласованная оценка **сквозного пути** — в §6.3.

### 5. Защитные меры — только зафиксированные в графе
Не придумывай меры защиты, которых нет в `controls`. Если guardrail есть — оцени его покрытие **конкретно по цепочкам**, через какие узлы каждая главная атака может обойти этот контроль. Если нет — это gap.

## Требования к содержанию отчёта

- **Раздел «Миссия»**: формулируй **не только** по типам узлов и рёбрам, но и по **реальному смыслу работы**, который следует из **системных и инструкционных промптов агентов** в JSON (`system_prompts` — в том числе записи с полем вида `dynamic->system_prompt` / `dynamic->system_message`; узлы роли `agent` и параметры `system_message`, `instructions` в `author_parameters_by_node`). Кратко сшей несколько промптов в единое описание миссии («для кого / что делает / в каких рамках»); укажи, какими **именами узлов из графа** это подкреплено. Чувствительные или длинные фрагменты **не** переписывай дословно — опиши назначение и поведение нейтрально (без воспроизведения ключей и секретов).
- **Раздел «Активы»**: для каждого актива укажи соответствующую поверхность атаки из эталона; отметь **crown jewels** в смысле флоу (данные пользователя, секрет в промпте, инструменты с внешним эффектом), опираясь только на JSON.
- **Раздел «Угрозы»**: компактная таблица-паспорт: Угроза | Узел/ребро | Поверхность атаки | Класс угроз | Kill chain в одной ячейке (кратко) | вероятность **в контексте отдельного звена**.
- **Раздел §6**: обязательно разбей подзаголовками 6.1–6.4 (ниже по шаблону). Здесь **богато** опиши kill chain’ы как основной объект приоритизации.
- **Раздел «Рекомендации»**: каждая мера должна указывать **какую цепочку** (имя из §6.1) или **узловую точку** (§6.2) она обрубает или ослабляет; приоритет **критично** отдавай действиям, закрывающим одним фиксом несколько достигаемых путей через choke point.
- В начале — **Раздел «Цели и границы»**: явно перечисли что in scope (какие узлы), что out of scope (например, инфраструктура за пределами JSON).

## 6. Kill chain’ы, риски, эксплуатация и наблюдаемость

### 6.1 Сквозные сценарии (end-to-end)
Для **каждой** главной достижимой атаки по топологии JSON построй блок в форме:
**Цепочка «<краткое имя>»** → финальный актив/эффект (узел или класс последствий).
- Перечень шагов **1→2→…→n**, на каждом шаге: имя узла из JSON (`id`/display name в обратных кавычках), используемое ребро/поле, что делает злоумышленник семантически.
- Одно предложение: почему **отдельные** шаги не выглядят как одиночная «critical CVE», но **переход** из шага в шаг возможен именно этим флоу.
- Вероятность **всего пути** на шкале высокая/средняя/низкая с обоснованием по топологии (наличие guardrail, длина пути).

### 6.2 Узловые точки (choke points) в топологии
Таблица или список: компонент/ребро из JSON → «через эту точку проходят цепочки A, B, …» → к каким активам ведёт сходящийся транзит → почему **одна** техническая правка здесь режет несколько атакующих историй одновременно.

### 6.3 Приоритизация рисков по путям (не изолированно по CVSS-аналогии)
Отсортированный список (топ минимум 3 полных цепочек): **название цепочки** | суммарный **риск по пути** (вероятность пути × тяжесть для бизнеса на концевом активе) | ключевые предпосылки.
Не дублируй «три medium»: покажи, какие три **композитные пути** важнее именно для **этого** графа.

### 6.4 Наблюдаемость и эксплуатация в реальности
Для **каждой** ключевой цепочки из 6.1 (не абстрактно по §5): что увидит защита/операционный контроль при прохождении цепочки (логи, аномалии токенов, аргументы tool calls, промежуточные `response`). Формат: строка вида цепочка → сигналы → если применимо, чем отличается «без звена X».

Конкретные меры с привязкой к узлу/ребру из JSON; для каждой укажи **какие цепочки** (имя из §6.1) или **узловую точку** (§6.2) нейтрализуются; приоритет: критично / важно / желательно.
